# RFC 0005 — N4 video engine and v1 implementation plan

**Status** — Release proposal. The [alpha contracts](../../docs/README.md) describe the implementation available to contributors.

The proposed product is a desktop video editor for product creators and independent media producers. One person can revise the production directly or with an agent. The release test is a complete revision cycle. A creator cuts footage, delegates an animated title, corrects it by hand, asks for another edit, reopens the project, and exports the approved picture and sound. The [creator brief](../docs/research/video-editor/creator-expectations.md) defines that experience. The [architecture overview](../docs/research/video-editor/architecture-overview.md) and [technical research](../docs/research/video-editor/technical-research.md) explain the candidate components. This RFC proposes where they live, in what order to build them, and what evidence advances the work.

## Recommended repository boundary

N4 incubates in its own repository as part of [nothing](https://github.com/gridaco/nothing). The implemented PoC lives under `spikes/` and can move as one package after review. For the implemented alpha, start with the [current contracts](../../docs/README.md).

```text
n4/
  docs/                           # current contracts, regressions and performance
  spikes/
    Cargo.toml, Cargo.lock        # Rust workspace and shared dependency versions
    engine/                       # n4-engine
      src/project/, src/plan.rs   # authored document, validation and frame evaluation
      src/editor/, src/host/      # edit state, selection, playback and host commands
      src/media.rs, src/media/    # timestamp indexes and decoding
      src/render/, src/export.rs  # picture composition, audio mix and export
      src/bin/                    # CLI, persistent host and optional device tools
      fixtures/                   # small CC0 media and authored test inputs
    spatial/                      # scene types, OpenUSD importer and wgpu renderer
    host/                         # TypeScript kit and Electron harness
    sdk/python/                   # authoring helpers
    docs/, rfcs/, examples/       # studies, design proposals and public projects
```

The CLI can build without the windowing and device dependencies. Separate crates isolate the optional native SDK and the spatial renderer so contributors can exercise each contract independently.

**What should survive a format change.** An accepted edit produces a revision. Evaluation turns it into explicit requests at project and source times: a selected stream, a picture interval or audio sample range, and ordered drawing and mixing operations. Test those values without a window, decoder or GPU. FFmpeg owns the codec mechanics inside the media module. The renderer owns the GPU device, paragraph painter, intermediate surface lifetimes and compositing. Playback decides deadlines and which old requests to discard. A host supplies commands and consumes completed output. Keep file syntax, GUI event types and concrete codec handles out of the evaluated plan. Keep the plan private and allow its operations to grow as new semantics require.

**Promotion test.** Build the same small edit directly in Rust and through the provisional text loader. Compare the selected source times, layer order, audio intervals and final pre-encode frame at specified instants, including a trim boundary, a backward seek and a text-width edit. Reserve exact pixel comparison for the pinned renderer, font, color settings and quality. Keep the independent cue sheet, timing and cache traces, test media and the implementations that pass. The persisted schema, SDK spelling, fixture loaders and diagnostic UI can evolve. A genuinely new feature such as a temporal filter may extend both the model and the plan.

**Host and UX.** The offscreen CLI is the development entry point. The feature-gated SDL2 player presents completed native frames and plays the engine's PCM. The Electron kit exercises the same Rust contracts through a persistent child process. A shipping host still needs product and distribution qualification. [Host kit](../host/README.md)

## Contracts to settle before spreading code across packages

Use provisional project and SDK syntax during prototyping. The canonical edit is deterministic, directly editable text. A GUI save produces a readable diff, an agent can find an object with `rg` and patch it, and the editor can validate and reload the result. The CLI and SDK provide optional structured access. Rewrite the public specification before shipping v1, using the editing cases that survived the trials. For example, an ordinary group already gives its children free placement, so the prototype can omit a layout-mode field on every layer.

Study OTIO for editorial timing and nesting, Bevy for extraction and offscreen rendering, and [OpenUSD for 3D scene composition and exchange](../docs/research/video-editor/technical-research.md#openusd-as-a-3d-scene-reference). MLT informs source and composition behavior, and OpenFX informs effect requests. The [design precedents](../docs/research/video-editor/design-precedents.md) record the semantics to mirror and the separate evidence needed for interchange or plug-in hosting.

A layer or group can reference a filter and its parameters. The filter defines its controls, so a bundled or creator-supplied finish can use the same inspector and edit operations. Keep effect-specific properties out of the project schema. The [graphics trial](../docs/research/video-editor/poc-gates.md#p4--paint-animate-and-reuse-real-2d-graphics) can test this boundary before selecting a public shader interface.

The native CLI and SDL2 player call the library directly. The host kit uses a framed pipe protocol. A future Wasm target and a live per-frame extension ABI each need a demonstrated consumer.

## Prerequisite for maintained implementation

Run the [engineering PoC gates](../docs/research/video-editor/poc-gates.md) against the native package and a recorded machine profile. Write the engine slice to promotion quality during the PoC. Promotion to maintained scope is on hold until the native gates have passing evidence. A shipping client requires its own product and distribution review.

## How to qualify performance and distribution

Suggested first workload for review: 1080p SDR output at 30 fps on a named Apple Silicon Mac, one real variable-frame-rate screen capture, one long-GOP camera clip, two overlapping audio clips, and one transparent animated overlay. Include several minutes of source to distinguish cold seeks from warmed playback. Use original footage and proxy playback in separate runs. Record hardware, OS, native renderer and viewer builds, codec profiles, exact fixture revision and output settings.

The [PoC run card](../docs/research/video-editor/poc-gates.md#p0--fix-the-target-and-the-pass-criteria) freezes interaction, seek, playback, sync and memory criteria before measurement. Carry the accepted profile and evidence into release qualification. Human review covers legibility, edge fringing, audible joins and how the playhead feels on the actual display.

During incubation the package can use Cargo directly. Keep the default check, frame-render, export and replay workflows headless. Use the viewer for measured live trials; exercise the chosen desktop package when qualifying the shipping product. Choose compatible FFmpeg build flags, notices, signing and engine discovery before calling the installer ready.

## Scope and review decisions

**Proposed v1** includes a qualified Mac desktop build, editable picture/sound cuts, motion titles, directly editable projects, one shareable SDR export, SDK-defined sources backed by approved renders, and creator-defined image filters. Automatic anchoring and sibling layout are deferred. Screen capture itself, broad NLE interchange, multicam, feature-length qualification, HDR/ProRes mastering, a native 3D editor, hosted services and additional desktop platforms remain follow-on work. Linked media already provides a way to use externally rendered shots.
