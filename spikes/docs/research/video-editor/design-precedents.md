# Design precedents for the timeline, media sources and effects

The syntax measurements describe exploratory documents. [Signal Atlas](../../../examples/signal-atlas/project.proj) shows the master grammar accepted by the contributor build.

Design direction for review, November 24, 2026. The canonical artifact is an editable text production document. The desktop editor, CLI and SDK read the same document. An author can search it, edit a trim with ordinary text tools and reopen the result. Code supplies new source and effect behavior when a declaration needs an implementation. The public syntax remains provisional.

Three precedents answer different questions. **OpenTimelineIO (OTIO)** describes an editorial cut. **MLT** evaluates compositions assembled from media services. **OpenFX** specifies how a host and an image-effect plug-in interact. We intend to mirror the concepts below wherever they preserve an edit or make a new source behave predictably. A file adapter, an executable MLT project and a binary plug-in host are separate interoperability decisions. The [technical research](technical-research.md) covers the wider design.

## OTIO for the editorial model

OTIO's native timeline contains references to media and information about how to cut it. Adobe ships OTIO import/export in Premiere. A cut that can continue in another editor is a concrete reason to support the format at an exchange boundary. [OTIO overview](https://github.com/AcademySoftwareFoundation/OpenTimelineIO) · [Premiere release notes](https://helpx.adobe.com/premiere/desktop/whats-new/release-notes.html)

| Concept to mirror                           | How we would apply it                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source reference and placed clip            | Give two uses of the same source distinct clip identities, trims and placement. A source can identify a file, an image sequence or a generator. If the source is missing, preserve the reference and the edit so the user can relink it.                                                                                                                                           |
| Rate-aware time and named coordinate spaces | Carry a rate or time base with a time value. Distinguish the available range of the media, the portion selected by a clip, the range the clip occupies in its parent, and any extra material visible during a transition. Preserve a nonzero source start. For variable-frame-rate footage the decoder must resolve source presentation timestamps.                                |
| Range endpoints                             | Use start and duration and document an exclusive end for our calculations. At one frame rate, start 10 and duration 3 select frames 10, 11 and 12. An adjacent clip can begin at 13.                                                                                                                                                                                               |
| Sequence, layers and gaps                   | A track orders children in time. A stack combines children over the same span. Preserve explicit stacking order and intentional empty time. A gap lets lower picture show through. A deliberately black graphic draws black.                                                                                                                                                       |
| Nested compositions and trims               | An inner track or stack can occupy one slot in its parent and expose a trimmed portion of its contents. Extending that outer trim can reveal more of the inner edit. For repeated intros, our proposed named composition can also have several referencing instances with independent trims. Inline nesting alone says nothing about whether editing one intro changes the others. |
| Transitions, retimes, markers and metadata  | Represent a transition's two sides and required source handles. Represent a speed change or freeze through an explicit time mapping. Attach a marker or range to the object whose timing it follows. Give extension metadata a namespace when preserving it across a handoff. Coverage for each receiving application needs testing.                                               |

A timeline may also carry a global start time. Preserve its timecode origin when the destination can express it. Keep a local frame offset of zero distinct from a programme that starts at timecode 01:00:00:00. In our model, a frame rate such as 30000/1001 should retain its ratio across saves and conversions. [OTIO serialized timeline](https://opentimelineio.readthedocs.io/en/latest/tutorials/otio-serialized-schema.html)

The OTIO `Track`, `Stack`, `Clip`, `Gap`, `Transition`, `Marker`, media-reference and time-effect schemas are useful test cases when reviewing our design. Its serialized class names and object layout are choices for an OTIO adapter. A shared compound-clip definition is an additional product decision. Final Cut's edits to a parent compound clip illustrate what its instances should do if we choose that behavior. [OTIO timeline structure](https://opentimelineio.readthedocs.io/en/latest/tutorials/otio-timeline-structure.html) · [Time ranges](https://opentimelineio.readthedocs.io/en/latest/tutorials/time-ranges.html) · [Serialized schemas](https://opentimelineio.readthedocs.io/en/latest/tutorials/otio-serialized-schema.html) · [Final Cut compound clips](https://support.apple.com/nl-nl/guide/final-cut-pro/verca9e8672/12.3/mac/15.6)

### An asymmetric dissolve as a reference case

OTIO 0.18.1's track implementation computes a child's start by adding the durations of preceding non-overlapping children. For a transition it subtracts its incoming offset from that cut position. Its handle calculation uses different offsets for the tail of the outgoing clip and the head of the incoming clip. This is a compact check on the meanings of three N4 times. [OTIO track implementation](https://github.com/AcademySoftwareFoundation/OpenTimelineIO/blob/v0.18.1/src/opentimelineio/track.cpp#L47-L85) · [Handle calculation](https://github.com/AcademySoftwareFoundation/OpenTimelineIO/blob/v0.18.1/src/opentimelineio/track.cpp#L139-L154) · [OTIO time ranges](https://opentimelineio.readthedocs.io/en/v0.18.1/tutorials/time-ranges.html)

At 24 fps, trim A to source frames [110,120) and B to [210,218). The cut lies at inner frame 10. A dissolve with an in-offset of 2 and out-offset of 3 occupies [8,13). At frame 8 it needs A118 and B208. At frame 10 it needs A120 and B210. At frame 13 only B213 contributes. An instance of the inner section [4,16) beginning at episode frame 100 places the same dissolve at [104,109). Changing the spelling or organization of the fixture should leave these requests intact.

**Upstream check, November 24, 2026.** Ran this case with the upstream OTIO 0.18.1 Python wheel in an isolated temporary directory. Using a 100-frame gap followed by the trimmed inner track, `transition.range_in_parent()` gave [8,13) and `inner.transformed_time_range(range, outer)` gave [104,109). The clips' `visible_range()` results were A [110,123) and B [208,218). At the inner cut, `inner.transformed_time()` mapped frame 10 to A120 and B210. At inner frame 13, A123 is already outside A's visible range. These values supply an independent expected result for a native evaluator test.

N4 needs a native comparison against the asymmetric case, real-file interchange, variable-frame-rate decode accuracy and NLE round trips before claiming compatibility.

## MLT for the media runtime

| Concept to mirror                                 | How we would apply it                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Producer, cut and consumer                        | A source supplies media. A clip selects and maps its time. A preview or export consumer drives evaluation. With fixed inputs and settings, picture has the conceptual contract `frame(source_time)`. For audio, request a sample range so a cut can be mixed accurately across a picture-frame boundary. |
| Seeking with private execution state              | A provider may decode ahead, replay from an earlier point, use checkpoints or return an approved render. Let the host schedule requests by playback, scrub and export needs. Returning to a marked time must reproduce the same full-quality frame, including after a fresh open.                        |
| Playlists and multitrack composition as producers | MLT can feed the result of a playlist or multitrack tractor into another edit. A document-defined nested timeline, a decoded movie and an externally generated shot should likewise be placeable through the same source contract.                                                                       |
| Filters, transitions and attachment scope         | Order the effects on each source, use or composition. Adjusting ink on one chart instance affects that use. Filtering a composited group sees its children together. A two-input transition receives both sides of the edit.                                                                             |
| A declarative graph of services                   | A file can describe sources, uses, parameters and connections and leave execution to the engine. Our stable IDs and editable text should survive a GUI save and a subsequent file patch. Python can implement a new producer, or inspect and validate an existing production.                            |

MLT's producer API exposes seeking and its XML uses inclusive in/out frame positions. The three frames above map to `in="10" out="12"`. We can keep a different internal representation and perform the conversion at the boundary. MLT XML, its service identifiers, native plug-ins and callbacks belong to MLT integrations. For example, Kdenlive adds its own editing metadata to MLT project files. A successful render of such a file establishes less than an editable round trip. [MLT architecture](https://mltframework.org/docs/framework/) · [MLT XML examples](https://www.mltframework.org/docs/mltxml/) · [Producer playtime calculation](https://github.com/mltframework/mlt/blob/master/src/framework/mlt_producer.c) · [Kdenlive project files](https://docs.kdenlive.org/en/project_and_asset_management/file_management/project_files.html)

**Editor-owned behavior.** The host can obtain a thumbnail by asking for a reduced-size frame. A provider may supply a cheaper thumbnail or poster as an optimization. The timeline retains the clip's identity, trim and placement while a slow source renders or a provider is unavailable. A Blender scene can publish an approved render for playback. Changing a camera or regenerating the scene requires its provider and source assets. These are proposals for our host.

## OpenFX for the image-effect boundary

| Concept to mirror                           | How we would apply it                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Effect contexts and named inputs            | A generator can create a picture from parameters, a filter processes a source image, and a transition blends two inputs using progress. A matte or grain image may be another declared input. Separate required inputs from optional ones so wiring remains inspectable.                                                                          |
| Plug-in describes, host owns controls       | The definition declares names, types, defaults and which parameters can animate. The host handles inspection, persistence, keyframes and undo. Ship an outline or dry-ink filter through this same contract. The project records an ordered reference and parameter values, without an effect-specific document type or per-effect version field. |
| Time, render scale and image interpretation | Supply explicit request time, scale and image area, plus the supported pixel components, precision and alpha convention. Our compositor also defines the working color space and conversion at each boundary. Compare full-quality preview and export with matching settings.                                                                     |
| Output bounds and input regions             | Distinguish where the effect can write (region of definition) from what it needs to read for a requested output rectangle (region of interest). An outer outline expands the output. A blur can need input pixels beyond a tile edge. A full-frame implementation can establish correctness before tiling.                                        |
| Temporal dependencies and identity          | A motion effect may need neighboring samples to render one frame. A neutral filter can report that its output equals an input. The host can use declared inputs, parameter changes and request time to schedule work and reuse results.                                                                                                           |

An OpenFX _clip_ is a named image input or output on an effect instance. In our editor, _clip_ means a timed placement of a source. A custom transition can sample two inputs while the parent track continues to own the two editorial placements. [OpenFX image-effect contexts](https://openfx.readthedocs.io/en/latest/Reference/ofxImageEffectContexts.html)

Study OpenFX's optional capabilities, concurrency rules, sequence-render lifecycle and acceleration interfaces when a real effect calls for them. A small WGSL compositor trial can test the image contract independently of the eventual public language. Hosting third-party OpenFX binaries would require implementing the corresponding ABI, suites, actions and supported contexts and exercising actual plug-ins. The reference applies to image effects. The production's timeline, audio mixer and custom clip lifecycle have their own contracts. [OpenFX contexts](https://openfx.readthedocs.io/en/latest/Reference/ofxImageEffectContexts.html) · [Parameters](https://openfx.readthedocs.io/en/latest/Reference/ofxParameter.html) · [Image-effect actions](https://openfx.readthedocs.io/en/latest/Reference/ofxImageEffectActions.html)

## Evidence that would change a compatibility claim

These cases give the existing [PoC gates](poc-gates.md) editorial and rendering examples. A claim about another application needs a test through that application.

1. **Text and time.** Put two different trims of one numbered source around a gap. Change one trim in the GUI, inspect the text diff, patch the other trim externally, then reload and scrub the cut. Confirm identities, the first and last included frames, and an independently timed audio cue. An invalid patch or conflicting unsaved edit must leave the last valid production recoverable.
2. **Nesting and reuse.** Use the same named intro twice with different outer trims. Edit its title once and check both occurrences. Edit an inline copy and check that only that occurrence changes. The before/after document should explain the difference.
3. **Editorial handoff.** Export a supported subset to OTIO and open it in a named version of Premiere or Resolve. Verify clip order, source identity, trim endpoints, handles and sync against a cue sheet. For a Blender clip, reference its approved render and map its frame origin to the intended cut. Report whether the receiver can trim that render and which source controls survive. Record anything baked or omitted.
4. **Effect and runtime.** Request a custom shot forward, backward and by direct seek. Apply one dry-ink definition to a graphic, footage and a mixed group. Compare the approved preview with the pre-encode export. An MLT interoperability claim would additionally need a real MLT project and identified services. An OpenFX hosting claim would need a named plug-in, host platform and exercised capabilities.

Codec and container names describe a separate delivery promise. For example, an H.264/AAC MP4 export is judged by its encoded streams, timestamps, metadata and playback in an independent decoder. Similarity to an OTIO timeline, MLT graph or OpenFX effect descriptor gives no evidence about that file.
