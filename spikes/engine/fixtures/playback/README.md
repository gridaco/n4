# Native device workload

From the engine directory, create the 120-second workload in a new directory with at least 300 MiB available. The generator uses the supplied N4 Grid Sans font, FFmpeg test patterns and two tone bursts. It needs FFmpeg with libx264, ffprobe and Python 3.8 or newer. The two-minute 4K source repeats ten seconds of original imagery over 3,600 distinct presentation timestamps. It contains closed 75-frame GOPs with B frames. Probe metadata and exact source digests are saved beside the project.

```sh
python3 fixtures/playback/prepare.py /tmp/n4-play-load
env LIBRARY_PATH=/opt/homebrew/lib cargo build --locked --features device-probe --bin n4-device
python3 fixtures/playback/run.py /tmp/n4-play-load/project.json \
    --device target/debug/n4-device --out /tmp/n4-play-loaded
```

The workload driver starts one FFmpeg worker per job class. Each worker requests a new time range every two seconds and writes a real filmstrip, waveform or 640×360 proxy into temporary storage. A slow worker finishes its current request before taking another. All three must be active before the native probe begins. A child error or early exit fails the run. The driver samples process-tree RSS once per second and records generated bytes, ranges and timestamps in `load.json`. The device report and logs are retained even when a run misses its timing budget. The driver needs access to `ps`, a physical display and a sound device. Codec and OS workers outside the process tree and independent GPU allocations can require separate measurement.

For a control run add `--unloaded` and choose a fresh output directory. `--seconds N` shortens playback for debugging and `--seek-count N` changes the warm/fresh seek count. Keep the 120-second, 30-seek loaded run for the performance decision.

## Ten-cycle memory trial

```sh
cargo build --locked --example load_cycles
python3 fixtures/playback/cycles.py /tmp/n4-play-load/project.json \
    --probe target/debug/examples/load_cycles --out /tmp/n4-cycle-memory.json
```

This trial keeps one headless preview and a 160×90 source filmstrip open for ten identical rounds. Each round plays 48 distinct frames (larger than the 1080p frame-cache window), sends a burst of scrubs through both workers, rejects an old ticket and consumes the latest picture and thumbnail. Two FFmpeg jobs also produce a waveform and proxy each round. Process-tree RSS is sampled every 200 ms and again at the drained endpoint of each cycle. A per-cycle record includes the returned frame identities, background bytes and RSS. The run exits unsuccessfully if peak RSS exceeds 1.5 GiB or the tenth drained endpoint grows more than 64 MiB above the first warm endpoint. It requires the native offscreen compositor and process-tree sampling privileges.

## Random-access decoder comparison

```sh
python3 fixtures/playback/seek_variants.py /tmp/n4-play-load/long-gop.mp4 --out /tmp/n4-seek-variants.json
python3 fixtures/playback/seek_variants.py /tmp/n4-play-load/long-gop.mp4 \
    --loaded --variants software_4 software_8 --out /tmp/n4-seek-loaded.json
```

The script decodes from the beginning to establish independent SHA-256 hashes at the 30 device-probe locations. It then interleaves fresh FFmpeg processes in a seeded order at each location, using the same transform and pipe read as the native decoder. The reported latency ends when all 1080p RGBA bytes are available in CPU memory. The VideoToolbox variant explicitly downloads from a hardware surface and requires access to the Mac media device. The loaded software-only comparison repeats the three background jobs.
